# Content System Contract

## Source and rendering

- English blog articles are authored in `content/blog/*.md` using the existing frontmatter conventions.
- The Markdown file is the content source; the rendered route, index, metadata, and schema are runtime outputs to verify.
- Do not create duplicate `.txt` or alternate content systems unless the repository architecture explicitly requires one.

## Publication integrity

Verify slug, title, description, excerpt, H1, publication date, canonical URL, author/source fields, CTA, internal links, and rendered article text. Use current canonical slugs discovered from the repository, not remembered routes. A new article must appear exactly once in the intended index and sitemap where the current architecture requires it.

## Claims and sources

Preserve the approved search intent and meaning. Verify current technical/research claims against primary sources. Preserve preprint, benchmark, aggregate, tested-settings, and illustrative-scenario qualifications. Never fabricate clients, results, benchmarks, citations, implementation experience, or business outcomes. An illustrative scenario is not a case study.

## Links and approval

Use restrained contextual internal links and the existing CTA convention. Do not add automatic commercial blocks to an article without an explicit content decision. Human editorial/business approval is required when wording changes the meaning, claim strength, positioning, or commercial implication.
